세 실험은 무엇을 실행하는가?

① 채널 함수 단독이미 준비한 IQ → 입력 준비·필요한 GPU 복사 → 채널 계산 → 결과실제 UE·gNB·ZMQ 없음. GPU kernel과 함수 전체 시간을 구분.

스레드와 CPU 코어는 무엇이 다른가?

스레드는 진행할 작업 흐름, CPU 코어는 그 작업을 실제로 실행하는 자리다. 입력 수신·채널 처리·출력 응답을 서로 다른 스레드가 맡을 수 있다. 한 작업이 기다리는 동안 다른 작업을 실행할 수 있지만, 스레드를 늘린다고 코어가 늘지는 않는다.

여기서 ZMQ I/O 작업자 2→4개는 emulator의 여러 IQ 연결이 공유하는 입출력 담당 수를 늘린 것이다. 지나치게 늘리면 CPU 차례·메모리·동기화 경쟁이 커질 수 있다. 현재 자료가 증명한 것은 해당 더미 24 경로에서 4개가 2개보다 낫다는 것까지다. 두 코어만 배정한 실제 broker에 이 설정을 그대로 옮겨 성공을 보장하지 않는다.

코어 공유는 어디서 일어나는가?

아래는 이번 실제 라이브 비교의 CPU affinity 배치다. gNB 5–12, emulator 15–16, UE 13·14·17–19, 보조 작업 0–4를 사용했다. 코어를 누르면 어떤 작업들이 그 실행 자리를 나누는지 볼 수 있다.

어느 프로그램 안에서 지연됐는가?

516 µs는 가운데 emulator의 CPU에서 생긴 지연이다

채널 에뮬레이터는 GPU 채널 함수만을 뜻하지 않는다. IQ를 받고, 버퍼를 관리하고, GPU 작업을 시작하고, 결과를 보내는 CPU 코드도 emulator의 일부다. 아래 빨간 지점은 그 CPU 코드에 있다.

PR의 16 UE·20 MHz·1×1, gNB로 들어가는 UL 신호 기준. 세 박스는 같은 Spark 안의 프로세스들이며 컴퓨터 세 대가 아니다. 작은 화면에서는 그림을 좌우로 움직여 볼 수 있다.

무엇이 아직 불명확한가: 과거 PR에 실린 두 CUDA gNB의 약 0.53배는 새 실행에서 재현되지 않았다. 이를 일반적인 두 셀 한계나 GPU context 전환 비용으로 단정하지 않았다. 프로세스 수와 함께 CPU·I/O thread 수도 변하므로 원인을 추가로 분리해야 한다.

따라서 이 축의 결과는 “같은 Spark에서 여러 실제 셀이 실시간을 완전히 유지하지 못했다”까지다. 16 UE에서 확인한 내부 스레드 병목이 두 셀의 모든 손실을 설명한다고 확대하지 않는다.

실제 PHY가 없는 더미 IQ 입출력의 스케일링

실제 PHY/MAC 없는 합성 radio 생성기 → ZMQ → emulator → ZMQ → 수신기 구성이다. 20 MHz·1×1, 고정 8-tap, broker 10개 코어, 합성 endpoint 5개 big core, ZMQ I/O thread 2개다. 실제 스택의 두 코어 broker 실험과 CPU 자원부터 다르다.

24 UE에서 ZMQ I/O thread만 2→4개로 바꾸자 0.661→0.873배가 됐다. 이 조건에서는 host IQ 전달 처리 능력이 실제 제한이었다.

이 결과는 ZMQ 경로의 제한이 존재할 수 있다는 직접 근거다. 실제 16 UE의 대기 시간을 전부 ZMQ 전송 비용이라고 판정하는 근거는 아니다.
RTX 5090에서 64 UE 실시간이었다는 기록은?

보존된 64 입력 fan-in 자료는 실제 UE·gNB·ZMQ가 없는 순차 channel 호출 벤치마크였다. 64 입력의 GPU kernel 중앙값은 약 68 µs였지만 gNB 방향 전체 호출 중앙값은 약 1.198 ms, p99는 약 1.338 ms였다. 실제 64 UE live-stack 실시간 동작을 입증한 기록으로 사용할 수 없다.

또 76.7 µs CPU preparation 수치는 RTX 5090의 8 입력·명시적 복사 경로에서 나온 p99 요약이다. 현재 Spark의 프로세스 간 IQ 대기와 다른 측정이다. Spark 내부 직접 입력 경로는 이미 적용되어 있었다.

구체적으로 어떤 함수에서 시간이 흘렀나?

직접 기록한 함수는 wait_tick() → sched_yield()다. 준비 상태를 검사했을 때 입력·row·빈 공간이 없으면 현재 구현은 CPU를 양보한다. 그 사이 준비가 완료돼도 처리 스레드가 CPU를 다시 받아 이 호출에서 복귀해야 다음 검사를 한다. 입력 도착에 맞춰 기다리는 스레드를 즉시 깨우는 notification 경로는 이 기준 구현에 없다.

현재 상태: 새 실행 모드는 실험 옵션으로 남겨 두었고 기본값으로 채택하지 않았다. 준비 후 지연을 발견한 것은 유효한 단서지만, 그 부분을 바꾸면 전체 병목이 자동으로 사라진다는 가설은 이번 구현들에서 성립하지 않았다.

호환성을 유지하는 다음 개선 방향

ZMQ 형식을 바꾸기보다 통신·작업 큐·GPU 제출·완료와 IQ 공급자의 CPU 비용을 같은 시계로 측정해야 한다. 새 큐에서 기다리는 시간도 기록하고, 실제 무선 시간당 CPU 작업량과 전체 진행률을 함께 비교한다. 늦은 IQ를 0으로 채우거나 버리거나, 고정 1 ms가 찰 때까지 새 장벽을 만들어 성능을 꾸미지 않는다.

relay 실행·조건·결과 근거

확장 GPU UE를 CUDA gNB와 함께 연결한 결과까지 확인했다

최신 검증: 2026.10.30. 기존 FFT·PDSCH·LDPC GPU UE 바이너리를 사용했고 UE/gNB 애플리케이션 소스는 새로 바꾸지 않았다.

GPU로 처리한 범위와 CPU에 남은 일

구현 범위는 OFDM FFT, PDSCH 채널 추정·등화·복조·rate dematching·LDPC다. PDCCH/CSI 제어 처리, 결과 비트 정리·CRC·상위 스택 및 UL 송신 처리가 모두 GPU로 옮겨진 것은 아니다. 16 UE 진단에서 PDSCH 약 99.0%가 GPU 경로였고 FFT의 CPU 복귀는 0이었다. 지원 조건 밖의 SIB/RAR·재전송 등에는 CPU 경로가 남는다.

왜 GPU 계산이 빨라도 전체가 느려질 수 있나?

소스와 시간 기록에서 슬롯마다 CSI용 FFT와 그 뒤 수신용 FFT가 수행되고, GPU 모드에서는 각각 CPU가 완료를 확인한다. PDSCH를 받는 슬롯은 복호 결과를 쓰기 전 한 번 더 기다린다. CSI 이후의 CFO 보정이 중간에 있으므로 두 FFT를 단순히 중복 버그라 보고 제거하지 않는다.

16 UE의 별도 slot trace에서 32 PRB·MCS18·10,504-bit PDSCH 처리 중앙값은 CPU 173 µs, GPU 423 µs였다. 이 비교는 여러 CPU 코어의 UE를 모은 동일 할당별 진단이며, 앞의 계측 없는 진행률과 별도 실행이다.

GPU 작업 자체의 실행 구간 중앙값은 FFT 약 15 µs, PDSCH 약 151–157 µs로 blocking/spin 사이 큰 변화가 없었다. 첫 GPU 작업의 API 복귀 후 시작 지연 중앙값도 거의 0이었다. 현재 자료에서 큰 추가 비용은 GPU 실행 시작 대기보다 완료 후 CPU 복귀 쪽에 나타났다.

CPU 전환 기록을 함께 수집한 blocking 실행에서 PDSCH의 완료 후 복귀 시간 평균 약 210 µs 중 204 µs는 해당 UE 스레드가 CPU에서 실행되지 않은 시간이었다. CPU가 이 구간에서 다른 산술 연산을 오래 수행한 것이 아니다. 다만 완료 통보를 아직 못 받은 시간과, 이미 깨어나 CPU 차례를 기다린 시간의 비율까지 분리한 것은 아니다.

spin은 원인 확인용 대조이지 채택된 해결책이 아니다. 깨어나는 비용을 줄여도 CPU를 계속 점유해 다른 UE·I/O·스택 작업을 늦출 수 있다. 첫 blocking/spin profiler wrapper는 관찰 대상의 살아 있음·정리 판정에 문제가 있어 전체 run gate가 실패했다. 그 시간 기록은 진단에만 사용했다. 고친 wrapper의 blocking 재검증은 run gate와 30/30 구간을 통과했지만, 계측 포함 속도를 기본 성능으로 사용하지 않는다. 별도 커널 wakeup 추적도 PID namespace 필터·버퍼 문제로 원인 비율 귀속에 사용하지 않았다.

이 결과가 제시하는 개선 후보

작은 작업을 GPU로 옮길 때 계산 절감보다 제출·완료 왕복 비용이 커질 수 있다. 작은 FFT를 CPU에 남기는 대조, GPU 제출 묶기, CPU 제어 경계에서 불필요한 동기화 줄이기, 복호 핸들 사전 준비가 후보지만 아직 실시간 개선으로 검증하지 않았다. ZMQ 형식 변경은 이 완료 대기 비용을 고치는 데 필요한 전제가 아니다.

확인한 원인과 아직 확인하지 않은 부분

확인한 것

더미 IQ 스케일링에서는 공유 I/O 처리 능력의 영향이 대조로 확인됐다. 실제 16 UE 기준에서는 emulator의 준비 후 sched_yield 복귀 지연이 컸다. 새 GPU UE에는 GPU 계산 종료 뒤 CPU가 복귀하는 지연이 크게 추가됐고, spin 대조로 그 영향을 확인했다.

확인하지 않은 것

모든 스케일링 축의 근본 원인이 하나라는 결론, ZMQ 형식 자체의 고정 UE 한계, GPU UE나 relay 재설계로 실시간 경계가 넓어졌다는 결론은 없다. 완료 통보 지연과 runnable 상태의 CPU 차례 대기 비율도 미분리다.

현재 실행 결정: 실패한 relay 성능 후보를 기본값으로 바꾸지 않는다. GPU UE의 한 조건 이득이나 짧은 동기 대기 감소를 전체 live scaling 성공으로 바꾸어 보고하지 않는다. ZMQ 인터페이스를 유지한 채 IQ 입출력의 CPU 예산과 GPU 완료 경계를 각각 개선·검증한다.

측정의 유효성을 함께 읽기

16 UE 기본 GPU 비교는 측정 중 연결 해제가 있었다. 8 UE 기본 비교는 양쪽 30/30 KPI 유효였지만 starvation이 남았다. CPU/GPU가 같은 입력을 받아도 HARQ·MCS에 따라 실제 처리량은 달라졌다. 원래 전체 live runner에 Nsight를 씌우는 방식은 실패했지만, 이번에는 UE 프로세스 내부에서 타임라인 수집에 성공했다. 수집하지 않은 Unified Memory 이동이나 GPU SM 점유율은 측정했다고 쓰지 않는다.
