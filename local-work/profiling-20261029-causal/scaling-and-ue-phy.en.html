How is a thread different from a CPU core?

A thread is a flow of work; a CPU core is an execution resource. Different threads can receive IQ, process a channel, and serve outputs. Waiting in one task can let another task run, but creating threads does not create cores.

ZMQ I/O workers 2→4 means adding workers to the shared I/O pool serving the emulator's IQ connections. Too many workers can increase scheduling, memory and synchronization contention. The evidence establishes that four beat two for the stated 24-path dummy test, not that every larger count improves performance. It also does not guarantee a gain with only two broker cores in the live setup.

Which function actually consumed the elapsed time?

The directly instrumented function was wait_tick() → sched_yield().When a readiness check finds no input, row, or free space, the current implementation yields the CPU. Even if readiness changes in the meantime, the producer must regain the CPU and return from this call before checking again. The baseline implementation has no notification path to wake the waiting thread immediately upon input arrival.

Why does this structure become unfavorable as UE count grows?

  1. Separate workers receive input at each radio port, advance channel processing per receiver, and serve results.
  2. At 16 UEs and 1×1, there are 51 relay workers alone. Including I/O and control, 63 threads were observed. They share the broker's two big cores.
  3. The current internal wait mechanism repeatedly performs sched_yield(). Workers without input remain runnable and take turns competing for CPU.
  4. Consequently, even when IQ, a request, or free space becomes available, the worker responsible for the next step cannot run immediately. Sample-level post-readiness delays and OS runnable waits jointly support this behavior.

Two instrumented runs reproduced input-ready delays of 545/540 µs and request-received-to-row-dequeue delays of 274/281 µs. “GPU channel computation has headroom” does not imply “the entire emulator is free of bottlenecks.”

Next directions while retaining compatibility

Keep ZMQ framing and measure communication, application queues, GPU submission/completion, and IQ-supplier CPU work on one clock. Include time waiting in new queues, CPU work per radio second, and overall progress. Do not manufacture performance by zero-filling or dropping late IQ, or by imposing a fixed 1 ms barrier that live peers may not be able to fill.

GPU coverage and remaining CPU work

The port covers OFDM FFT, PDSCH channel estimation, equalization, demodulation, rate dematching and LDPC. PDCCH/CSI control processing, bit unpacking, CRC, subsequent stack work and all UL transmission processing have not all moved to the GPU. In the 16-UE diagnostic trace, approximately 99.0% of PDSCH used GPU processing and FFT fallback count was zero. Unsupported SIB/RAR, retransmission and other conditions retain CPU paths.

Why can faster GPU computation produce slower overall progress?

Source and traces show a CSI FFT followed by a receiver FFT in each slot. GPU mode waits for each to finish before CPU consumers proceed, and a PDSCH slot waits again before using decoded results. CFO correction occurs after CSI, so the two FFTs must not simply be removed as an assumed duplication bug.

① GPU · CSI FFTGPU finishes → CPU completion wait
② CPU · CSI / CFO correctionCPU consumes GPU results
③ GPU · receiver FFTGPU finishes → CPU completion wait
④ CPU · PDCCHInterpret reception control information
⑤ GPU · PDSCH / LDPCGPU finishes → CPU completion wait
⑥ CPU · unpack / CRC / stackUse results in subsequent stack processing

In a separate 16-UE slot trace, median PDSCH time for the same 32 PRBs, MCS18 and 10,504-bit TB was 173 µs on CPU versus 423 µs through the GPU path. This allocation-stratified diagnostic pools UEs on heterogeneous CPU cores and is separate from the uninstrumented progress comparison above.

Candidate improvements suggested by the evidence

For small GPU jobs, submission and completion round trips can cost more than the computation saved. Candidates include retaining small FFTs on CPU, grouping GPU submissions, reducing synchronization around CPU control boundaries, and preparing decoder handles in advance. These have not been validated as real-time fixes. Changing ZMQ framing is not a prerequisite for addressing this completion cost.

Primary CPU/GPU comparison evidence · Completion delays, CPU-switch evidence and exclusions

Confirmed causes and remaining attribution limits

Confirmed

Dummy-IQ scaling is sensitive to shared I/O service capacity. The real 16-UE baseline had large emulator sched_yield return delays after readiness. The expanded GPU UE adds substantial CPU-return latency after GPU execution, whose sensitivity to blocking was established by a spin comparison.

Not established

No single root cause explains every scaling dimension. No fixed UE limit is established by ZMQ framing. Neither the GPU UE nor the relay redesign has expanded the measured real-time boundary. Completion notification and runnable scheduling delay remain unsplit.

Current execution decision: Keep failed relay performance candidates out of defaults. Do not relabel a gain in one UE condition, or a shorter fence, as overall live scaling success. Retain ZMQ compatibility while improving and validating IQ-I/O CPU budgets and GPU completion boundaries separately.

The primary 16-UE GPU comparison had connection loss during measurement. Both 8-UE primary runs had 30/30 valid KPI segments, with starvation remaining. Identical input bundles still produced different MCS/actual payload under HARQ. Profiling the whole live runner previously failed, but targeted profiling inside the UE process now succeeded.
