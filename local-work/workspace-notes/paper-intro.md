# 인트로 작성 가이드 — GPU 채널 에뮬레이터

작성 2026-10-02 (2판: 상사 피드백 반영). 기준 트리 `integration-0928` (cb04f6c). 선행연구 상세 표는 `paper-contribution.md`, ACHEM·Tiny-Twin 실측 규모는 `prior-work-scale.md`, 10-02 lock-step 파이프라이닝 실험은 `SPARK_MILESTONES.md` S17 초안에 있다.

상사 피드백 두 가지: (1) 메인 기여가 GPU와 단단히 묶여 있지 않다 — "실시간 다중 안테나"에 왜 GPU가 필요한지 말해야 한다. (2) 세 갈래(time consistency, GPU memory, adaptivity)는 GPU 채널을 가능하게 하기 위한 설계 과제다 — 각 과제가 왜/어디서 생기는지와 그것을 위해 무엇을 했는지를 인트로에서 짝지어 설명해야 한다. 덧붙여 선행연구가 간섭(interference)을 어떻게 다루는지가 차별점이 될 수 있다.

## 1. 코어 기여 (하나)

> **실제 NR 스택을 끼운 채널 에뮬레이션에서, 링크·안테나·대역폭 규모가 커져도 슬롯 데드라인 안에 채널 연산을 끝내는 GPU 기반 시스템.**

규모의 세 축은 수신기당 링크 수(간섭·다중 UE·다중 셀), 포트 쌍(다중 안테나), 샘플 수(대역폭)이고, tap 수가 곱해진다. 간섭은 그중 "수신기에서 전부 더해야 하는 링크 수"를 키우는 대표 사례라 CPU의 링크별 스레드 방식이 깨지는 지점을 가장 잘 보여 준다(ACHEM 수치). 왜 GPU인가는 바로 아래 숫자로, 어떻게는 세 과제와 노드 단위 설계로 이어 쓴다.

### 왜 GPU인가 — 규모가 수신기당 연산량을 곱셈으로 키운다

"다중 안테나 실시간"만 보면 GPU가 꼭 필요하지 않다. 2×2 한 링크는 CPU로도 된다. GPU가 필요해지는 지점은 **간섭**이다.

- 간섭을 흉내 내려면 수신기마다 자기에게 들어오는 **모든** 송신기의 신호를 각 링크의 채널로 통과시켜 **같은 시간 축에서 더해야** 한다. 수신 노드 하나의 슬롯당 일은 `(들어오는 링크 수 L) × (포트 쌍 P_tx·P_rx) × (tap 수 K) × (슬롯 샘플 수 ∝ B)`의 MAC(multiply-accumulate)이고, 여기에 링크마다 페이딩 계수 생성(Jakes, Rician, 공간 상관)과 ray-traced 갱신이 얹힌다.
- 3셀 7 UE 정도의 평범한 간섭 시나리오만 돼도 링크는 수십 개다. 100 MHz(61,440 샘플/슬롯), 2×2(포트 쌍 4), TDL 12 tap, incoming 링크 30개면 수신 노드 하나가 슬롯(500 µs)마다 약 9×10^7 복소 MAC, 초당 약 1.8×10^11이다. CPU 한 코어(실효 수십 GMAC/s)의 몫이 아니고, 페이딩 계수 생성과 공간 상관이 그 위에 얹힌다.
- 선행 CPU 에뮬레이터는 이 합산을 **링크마다 스레드 하나**로 나누고 수신기에서 직렬로 더한다. ACHEM은 수신기 하나가 소스 16개에서 1 ms, 64개에서 2 ms라고 스스로 보고하고, 수신기 쪽 중첩(superposition)이 "V-USRP 처리 오버헤드의 주원인"이라고 쓴다. 500 µs 슬롯 기준으로는 소스 16개 전에 끝난다. Tiny-Twin은 단일 셀이라 셀 간 간섭 자체가 future work다.
- GPU에서는 "수신 노드 하나의 모든 링크 × 포트 × tap"이 커널 한 번의 배치다. 우리 측정: GB10에서 수신 노드 하나에 소스 64개 fan-in이 177 µs(호출시간 p50), 커널 35 µs. 즉 GPU는 **간섭 규모의 중첩을 슬롯 안에 넣는 수단**이고, 그래서 메인 기여는 "다중 포트 실시간"이 아니라 **"간섭이 있는 다중 링크·다중 포트를 슬롯 안에"**로 써야 GPU와 묶인다.

### 그런데 GPU를 끼우면 세 가지가 깨진다 — 그것이 세 갈래다

GPU 커널이 빠른 것은 출발점일 뿐이다. 실제 스택을 ZMQ로 끼운 채 그 커널을 매 슬롯 돌리면 세 가지 설계 과제가 생기고, 이 셋을 푼 것이 시스템 기여다. 각 과제는 **왜 생기는가 → 무엇을 했는가**를 한 쌍으로 인트로에 쓴다.

| 과제 | 왜 생기는가 (간섭·다중 포트·GPU에서 파생) | 무엇을 했는가 (메커니즘) |
|---|---|---|
| **T. Time consistency** | 간섭 합산은 **같은 샘플 인덱스**에서 더해야 의미가 있다. 그런데 링크마다 송신기가 다른 프로세스이고 ZMQ 요청-응답으로 제각각 도착하므로, 포트·링크마다 따로 처리하면 수신기가 서로 다른 시간 구간의 신호를 더하게 된다. 다중 안테나는 여기에 "같은 링크의 포트들이 같은 H[n]을 봐야 한다"를 더한다. | 수신 노드마다 **공통 샘플 epoch**와 **링크별 소스 커서**를 두고, producer 하나가 모든 incoming 링크에서 같은 길이의 창을 떼어 **한 번의 superposition 호출**로 처리한 뒤 소스 커서를 같은 양만큼 전진시킨다. 첫 슬롯에서 모든 링크 커서를 **co-initialise**, 늦게 붙은 송신기는 **커서를 frontier에 snap**(late-joiner), 아직 샘플이 없는 송신기는 **cold-source admission**으로 0을 더하지 않고 기다리거나 명시적으로 뺀다. 늦은 슬롯은 밀리지 않고 **strict-realtime drop**. 갱신은 처리 경계에서 노드 전체에 한 번에 적용. |
| **M. GPU memory** | 링크 수 L이 커지면 경로마다 입력을 복사하는 순간 메모리 이동이 MAC보다 커진다(입력 스트림은 송신 포트 수 P_tx개뿐인데 경로는 L·P_tx·P_rx개). tap history와 페이딩 grid는 링크·포트·tap·대역폭에 비례해 자라고 매 슬롯 CPU↔GPU를 오가면 안 된다. 분리 GPU는 PCIe, 통합 GPU는 소프트웨어가 남겨 둔 중간 복사가 병목이고, 한 대 박스에서는 CUDA gNB와 메모리를 나눠 쓴다. | 노드 안에서 **고유 송신 입력을 한 번만 준비**하고 경로들이 참조(소스 테이블, 최대 128 소스). **history와 페이딩 grid를 GPU 상주**, 계수 생성과 적용을 분리해 같은 링크의 안테나 경로 grid를 모아 공간 상관을 적용. 플랫폼별 데이터 경로: device 복사(RTX), mapped host memory(Orin), **호출자 버퍼 직접 읽기/쓰기**(GB10, pageable access). GB10 N=64 호출시간 934 → 177 µs, CPU 입력 준비 524 → 7 µs. |
| **A. Adaptivity** | 간섭 시나리오는 정적이지 않다. 이동·ray tracing으로 링크의 H가 실행 중 바뀌고, 그 갱신이 (a) 모든 포트에 같은 슬롯 경계에서 적용되어야 T가 유지되고, (b) history를 지우지 않아야 M이 유지되고, (c) 갱신율 r이 올라가도 슬롯 안에 들어야 한다. | 제어면(REQ/REP + PUB telemetry)이 갱신을 **노드 처리 경계**에 묶어 적용. 계수만 바뀌는 갱신(gain/phase)은 history 보존, 지연·경로 수가 바뀌면 선언된 warmup. 외부 producer(Sionna RT)가 프로세스 밖에서 10 Hz로 행렬을 보냄. **한계:** 지오메트리 변경 시 연속성은 미해결(future work). |

### 기여가 아닌 것
GPU라서 빠르다(2018 GPU MIMO, 2023 CUDA 3GPP), 실제 스택과 붙였다(Tiny-Twin, ACHEM), MIMO를 지원한다(ACHEM 명시), Sionna를 연결했다(Sionna RK, OWDT). 넷 다 선행이 있다.

### 증명 책임
P×B×L을 키울 때 CPU 에뮬레이터(같은 broker의 CPU 백엔드 + ACHEM/Tiny-Twin 수치)가 데드라인을 놓치는 지점 너머에서 우리가 돌린다는 **feasible region 곡선**. 축은 (i) 수신기당 소스 수(ACHEM Fig. 16과 같은 축), (ii) 포트×대역폭. 그리고 간섭 시나리오(2셀 이상, UE↔UE 없음)에서 y=Σ H_l x_l이 같은 샘플 인덱스에서 더해졌다는 **정합 검증**(X 트랙 V1–V4).

## 2. 선행연구는 간섭을 어떻게 다루나 — 차별점

| 연구 | 간섭 모델 | 실제로 보인 것 | 우리와의 차이 |
|---|---|---|---|
| **Colosseum / MCHEM** | 256×256 모든 쌍에 4-tap FIR, FPGA가 한 클록으로 합산 | 진짜 다중 노드 간섭, 실제 스택 | 간섭의 기준점. 하지만 공유 FPGA 테스트베드, tap 4개 고정, 상용 한 대로 불가 |
| **ACHEM** | N 송신 × N 수신 채널을 수신기 스레드에서 중첩 | 벤치: 수신기 1개 ← 소스 16개 1 ms, 64개 2 ms; N×N은 20 MHz/0.5 ms에서 L≈25–36에 drop 10 % 초과(5 ms 기준). **라이브는 2 노드 1×1** | 소프트웨어 간섭의 CPU 한계를 수치로 보여 준 유일한 선행. 우리는 같은 축에서 GPU fan-in 64 소스 177 µs |
| **Tiny-Twin** | 단일 셀, UE마다 독립 convolution, 셀 간 간섭 없음 | 10 UE | 간섭은 future work("multi-base-station, ICI") |
| **Sionna Research Kit** | 단일 링크 SISO | 1 UE | 간섭 없음 |
| **OWDT** | 단일 UE ray tracing | 상용 UE 1대 | 간섭 없음 |
| **OAI rfsimulator** | 여러 UE가 한 gNB에 붙되 채널은 UE별 독립 적용, 셀 간 합산 없음 | — | 수신기 쪽 합산이 없어 간섭 아님 |
| **우리** | 토폴로지의 모든 송신 포트→수신 포트 엣지를 수신 노드에서 **같은 샘플 창**으로 합산, 포트에 carrier 의미(다른 반송파 엣지 거부) | 2 gNB + 2 UE Sionna 모드, 두 TDD 셀의 서로 다른 패턴에서 UE↔UE 교차 링크 간섭(CLI) 첫 물리 재현(X5), 멀티 UE 엄격 판정 | 소프트웨어·상용 GPU 한 대에서 간섭을 실제 스택과 슬롯 안에 |

**간섭을 다루며 얻은 교훈(별도 절 후보):** 포트 기반 에뮬레이터가 반송파를 모르면 물리적으로 존재하지 않는 간섭(FDD UE↔UE)을 더하고, 드라이버의 송신 스케일 차이(srsUE +64 dB)가 그 가짜 간섭을 +62 dB로 키워도 게이트는 통과로 나온다. 수정: 포트 carrier 라벨, 장치별 tx_scale 정규화, strict attach 판정. "간섭 에뮬레이션은 합산이 빠르기만 하면 되는 게 아니라 무엇을 더할지 알아야 한다"는 메시지.

## 3. 문제 정식화 (제약식) — 간섭을 변수에 넣는다

워크로드 w = (L 링크 수, P 포트, K tap, B 대역폭, r 갱신율, U UE), 하드웨어 h = (데이터 이동 대역폭 β, GPU 메모리 M_gpu, SM 수). 수신 노드마다 슬롯당:

```latex
T_{\mathrm{slot}} = T_{\mathrm{move}}(L, P, B;\ \beta) + T_{\mathrm{coef}}(L, P, K, r) + T_{\mathrm{sum}}(L, P, K, B;\ N_{\mathrm{sm}}) + T_{\mathrm{ring}} \;\le\; \tau
```

```latex
M = M_{\mathrm{history}}(L, P, K, B) + M_{\mathrm{src}}(P_{tx}, B) + M_{\mathrm{coef}}(L, P, K) + M_{\mathrm{stack}} \;\le\; M_{\mathrm{gpu}}
```

- T_sum이 간섭 항(L에 선형)이고 GPU가 줄이는 항이다. T_move가 M 갈래, T_coef·r이 A 갈래, 그리고 "모든 항이 같은 샘플 창 위에서"가 T 갈래의 전제다.
- CPU 에뮬레이터는 T_sum을 링크 스레드로 나눠 수신기에서 직렬 합산하므로 L에 대해 지연이 선형으로 는다(ACHEM Fig. 16). 우리는 노드 단위 커널로 L을 배치 차원에 넣는다.
- 그림 하나: x축 L(수신기당 소스), y축 p99.9 T_slot, τ=500 µs 선. ACHEM 곡선(16 소스 1 ms)과 우리 곡선(64 소스 177 µs)이 같은 그림에 들어간다. 두 번째 그림: x축 P×B.

## 4. 인트로 문단 뼈대

| 문단 | 역할 | 핵심 문장 (초안) |
|---|---|---|
| 1 | 동기 | 5G/6G 스택 검증은 실제 스택을 실제 채널 조건, 특히 **다른 송신기들의 간섭** 속에 넣어야 한다. 공중파는 재현이 안 되고 RF 하드웨어 에뮬레이터는 비싸거나 공유 자원이다. |
| 2 | 현재 한계 | 소프트웨어 에뮬레이터는 링크마다 스레드를 두고 수신기에서 직렬로 더한다. 간섭 소스가 늘면 수신기 지연이 선형으로 늘어 슬롯 데드라인을 넘긴다(ACHEM 16 소스 1 ms). 단일 셀 에뮬레이터는 간섭을 다루지 않는다(Tiny-Twin, Sionna RK, OWDT). |
| 3 | GPU로 가는 이유 | 수신기 하나의 "모든 링크 × 포트 × tap × 샘플" 합산은 커널 한 번의 배치다. GPU는 간섭 규모를 슬롯 안에 넣는 수단이다. |
| 4 | 그러나 (세 과제) | 실제 스택을 ZMQ로 끼운 채 그 커널을 매 슬롯 돌리면 세 가지가 깨진다. 링크마다 제각각 도착하는 샘플을 같은 인덱스에서 더해야 하고(T), 링크 수만큼 입력을 복사하면 이동이 연산을 삼키며(M), 실행 중 바뀌는 채널을 T와 M을 깨지 않고 넣어야 한다(A). |
| 5 | 통찰 | 세 과제는 모두 처리 단위를 **수신 노드**로 잡으면 한 번에 풀린다. 노드 하나 = 공통 샘플 epoch + 링크별 커서 + 한 번의 superposition 호출 + GPU 상주 상태 + 한 번의 갱신 경계. |
| 6 | 시스템 | ocudu-gpu-channel: ZMQ IQ 위에서 srsRAN·OAI·OCUDU와 연결, 상용 GPU 한 대(RTX 5090, Jetson Orin, DGX Spark GB10), Sionna RT가 실행 중 채널을 공급, 포트에 carrier 의미. |
| 7 | 기여 목록 | §5 |
| 8 | 결과 요약 | GB10 소스 64 fan-in 177 µs, 2×2 rank-2 DL 148 / UL 112 Mb/s NACK 0, 두 TDD 셀 CLI 재현, 100 MHz 1×1 실시간, 100 MHz 2×2 무부하 0.80× (lock-step 파이프라이닝 후), 로봇 폐루프. (헤드라인 곡선은 실험 후.) |

문단 3–5가 상사 피드백의 핵심이다. "GPU가 필요한 이유(간섭 규모) → GPU를 끼우면 생기는 세 과제 → 노드 단위라는 하나의 답"이 인트로의 척추다.

## 5. 기여 목록 (인트로 끝에 들어갈 형태)

1. **문제 규정.** 실제 스택을 끼운 간섭 에뮬레이션은 수신기마다 모든 링크의 중첩을 같은 샘플 창에서 슬롯 안에 끝내야 하는 feasibility 문제이고, 링크별 스레드 합산(CPU 선행)은 소스 수에 선형으로 깨진다(§3 제약식, ACHEM 수치로 뒷받침).
2. **수신 노드 단위 GPU 에뮬레이션.** 공통 샘플 epoch·링크별 커서·한 번의 superposition 호출로 시간 정합(T)을, 고유 입력 한 벌·GPU 상주 history/grid·플랫폼별 데이터 경로로 메모리(M)를, 노드 경계 갱신으로 적응(A)을 얻는 설계와 구현.
3. **간섭 의미론.** 포트에 carrier 의미를 부여해 물리적으로 없는 링크를 거부하고 장치별 송신 스케일을 정규화하는, 소프트웨어 간섭 에뮬레이션의 정확성 규칙(X 트랙).
4. **평가.** 소스 수·포트×대역폭 축의 feasible region(CPU 백엔드·ACHEM 대비), 데이터 경로 분해, 정합 검증(parity, y=ΣHx, 2셀 CLI 재현), lock-step 스택의 파이프라이닝(S17), 로봇 폐루프.

기여 2의 Adaptivity 한계(지오메트리 변경 시 연속성)는 기여 문장 안에 넣지 말고 §Limitations에 둔다.

## 6. 평가 축과 세 갈래의 대응

| 평가 | 갈래 | 상태 |
|---|---|---|
| feasible region (P×B 스케일링, CPU vs CUDA vs 통합 direct) | Time + Memory | **없음, 최우선** |
| 데이터 경로 분해 (copy / mapped / direct) | Memory | 합성 있음, 라이브 필요 |
| M(w) 실측 (링크·포트·tap별 GPU 메모리, CUDA gNB 공존) | Memory | 없음 |
| 정확성 (parity, y=Hx, rank-2 처리량, CIR 계측) | Time | CIR 계측만 없음 |
| 갱신율 r vs τ (Sionna 10 Hz → ? Hz, 위치→적용 지연) | Adaptivity | R0/R3 부분 |
| 로봇 폐루프 (RTF 1.0, 승률 vs 채널·과부하) | 셋 다 | R0–R4a |

데이터 경로 분해는 독립 축이 아니라 feasible region 곡선의 "왜 거기 있나"를 설명하는 하위 절이다.

## 7. 확인할 것 (상사 피드백 해석이 갈리는 지점)

- [ ] **"adaptivity"의 범위.** 채널이 실행 중 바뀌는 것(이동, ray tracing)으로 해석했다. 플랫폼 적응(RTX/Orin/GB10 경로 선택)도 포함인지 확인. 포함이면 §3.3에 "하드웨어 적응" 한 단락을 더한다.
- [ ] **제약식의 "or".** `<= (gpu memory) or (hardware time delay)`를 "두 제약을 각각 만족"으로 읽었다. "둘 중 하나가 바인딩되는 지점을 찾아라"는 뜻이었는지 확인. 후자면 feasible region 그림에서 어느 축에서 어느 제약이 먼저 걸리는지를 표시한다.
- [ ] **PCIe 항.** 분리 GPU에서만 의미 있고 통합 GPU에서는 공유 메모리 대역폭으로 바뀐다. 식에서 β_pcie를 "데이터 이동 대역폭"으로 일반화해도 되는지.
- [ ] **UE 수 vs 포트 수.** Tiny-Twin이 UE 수로는 CPU로 버틸 가능성이 크다. 헤드라인 축을 UE가 아니라 P×B로 잡는 데 동의하는지.
- [ ] **Sionna 위치.** 기여 3(제어면)으로 넣되 연속성은 future work로 두는 것에 동의하는지. 브리지 코드는 Hyunsoo Lee 기여라 공저 범위 확인 필요.
