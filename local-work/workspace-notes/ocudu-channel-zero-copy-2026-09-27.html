왜 했나

emulator의 CUDA 백엔드는 RTX 5090 같은 디스크리트 GPU를 기준으로 짜여 있었다. 슬롯(1 ms, 23,040샘플, 방향당 184 KB)마다 IQ를 pinned 버퍼에 모아 cudaMemcpyAsync로 GPU에 올리고, 결과를 다시 내려받았다. GB10은 CPU와 GPU가 같은 DRAM을 쓰지만, 코드가 복사를 직접 요청하니 복사는 그대로 일어났다.

그래서 09-26 측정에서 5090과 GB10의 emulator 처리 시간이 같았다(44.8 vs 43.6 µs). GB10은 복사가 조금 빠른 대신 GPU 계산이 2배 느렸다. 이번 작업의 목표는 통합 GPU에서만 쓰는 경로를 따로 만들어 이 복사를 없애는 것이었다. 출력은 복사 경로와 bit 단위로 같아야 한다는 조건을 걸었다.

정확히 한 일

  1. 설정 노브 runtime.cuda_host_memory: copy | zero_copy | auto. 기본값은 copy로, 기존 동작과 같다. auto는 cudaDevAttrIntegrated인 장치에서만 zero-copy를 고른다. 6fab580
  2. 입력·출력 버퍼를 mapped 메모리로. cudaHostAllocMapped로 잡고 GPU가 같은 메모리를 직접 읽고 쓰게 했다. 슬롯마다 하던 H2D·D2H IQ 복사가 사라졌다. 6fab580
  3. 출력 직접 쓰기(direct). 장치가 pageable 메모리에 접근할 수 있으면, 커널이 호출자(브로커)의 출력 버퍼에 바로 쓴다. 마지막 CPU 복사도 사라졌다. 6fab580
  4. 메타데이터 mapped화를 시험하고 뺐다. H2D는 1.5 µs 줄지만 모든 GPU 스레드가 그 값을 호스트 메모리에서 다시 읽어 커널이 8 µs 느려졌다. 측정으로 확인하고 기본값에서 제외했다. 6fab580
  5. 입력 직접 읽기(direct_in). 채널 커널이 소스 IQ를 한 버퍼에서 찾던 방식을, 소스별 포인터 표(DeviceSourceTable, __grid_constant__ 커널 파라미터, 최대 128개)로 바꿨다. GPU가 브로커 입력 버퍼를 그대로 읽으므로, CPU가 UE들의 IQ를 한 버퍼로 모으는 복사와 그 H2D가 사라졌다. 사용자가 많을 때 남던 최대 병목이다. 0a6f281
  6. 브로커 ring 복사 수정. IqRing::push/read가 샘플을 하나씩, 샘플마다 나머지 연산(%)을 하며 복사하고 있었다. wrap 전후 최대 두 번의 블록 복사로 바꿨다. 동작은 같고 CPU 백엔드도 혜택을 받는다. 0a6f281
  7. 계측 추가. ProcessorTimings에 host_prep_us, host_out_us, call_us, zero_copy를 넣었다. 벤치에는 같은 행, cuda_zero_copy(실제로 돈 모드), --per-node를 넣었다. 이 계측 덕분에 남은 병목이 CPU 입력 모으기라는 것을 찾았다.
  8. 검증 장치. copy와 zero-copy 조합 10가지를 4슬롯 동안 bit 단위로 비교한다. 3-UE fan-in과 ring 무작위 참조 모델 비교도 넣었다. 음성 대조군 3개(일부러 틀린 코드)가 모두 실패하는 것을 확인했다.
  9. 라이브 러너. OCUDU_NATIVE_CHANNEL_BUILD로 브로커 빌드 폴더를 바꿀 수 있게 해서, 두 번째 소스 트리로 게이트를 돌릴 수 있게 했다.
  10. 문서. README에 노브와 벤치 출력을 적었다. ZERO_COPY_MILESTONES.md에 단계별(Z0–Z8) 계획·근거·로그 위치를 남겼다.

무엇을 없앴나 — 슬롯 하나의 IQ 경로

라이브 브로커에서 한 방향 IQ(184 KB)가 거치는 단계다. 초록 테두리는 이번 작업으로 사라졌거나 빨라진 단계다.

사용자·대역폭이 늘수록 더 줄어든다

gNB 노드 emulator 호출 시간(p50). 막대 길이는 설정마다 copy를 100%로 둔 비율이고, 오른쪽 글자는 실제 시간이다.

copy (기존) Z5 · 입력·출력 zero-copy + 출력 direct Z8 · + 입력 direct (최종)
0%25%50%75%100% = copy
설정copyZ5Z8Z8 절감CPU 입력 모으기: copy → Z8
  • 대역폭: 없앤 복사들이 모두 바이트 수에 비례한다. 그래서 122.88 MS/s(100 MHz급)에서는 −74%까지 줄었다.
  • 사용자 수: gNB 하나가 UE N명의 업링크를 한 호출에서 합친다. copy에서는 N명의 IQ를 CPU가 모으는 복사(N64에서 524 µs)가 호출의 절반을 넘었다. Z8에서 이 복사가 사라져 N64에서도 177 µs다.
  • 슬롯 예산(30 kHz, 500 µs): Z5까지 넘던 N64(714 µs)와 N16 @ 92 MS/s(646 µs)가 177·145 µs로 예산 안에 들어왔다.
  • TDL-A(23탭)는 GPU 계산이 대부분이라 −19%에 그친다. 복사를 없애는 작업으로는 GPU 계산 시간을 줄일 수 없다.

한계와 남은 일

  • 기본값은 아직 copy다. Jetson Orin(Z6)을 검증하지 않아서 auto를 기본으로 바꾸는 건 보류했다. 지금은 설정에 cuda_host_memory: auto 또는 zero_copy를 명시해야 이 경로를 탄다.
  • 디스크리트 GPU에서는 쓰면 안 된다. 5090에서 zero-copy는 모든 접근이 PCIe를 건너 TDL-A가 43배 느려진다. auto는 이 경우 copy를 고른다.
  • 원인을 확인하지 않은 관측 세 가지. mapped 메모리 커널 비용과 pageable 읽기가 더 싼 이유, zero-copy에서 ring 단계가 copy보다 5–10 µs 긴 이유, 라이브 커널·H2D가 벤치보다 5–7 µs 큰 이유. 모두 nsys나 ncu로 확인하지 않았다.
  • MIMO 출력(행 2개 이상)은 출력 direct를 쓰지 않는다. 소스가 128개를 넘는 노드는 입력 direct 대신 예전 모으기 방식으로 돌아간다.
  • 다음 후보. 라이브와 벤치의 차이 분리, step 메타데이터 H2D(3–8 µs) 제거, ring을 거치지 않는 경로(브로커 구조 변경).
