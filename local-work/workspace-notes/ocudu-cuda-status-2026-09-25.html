Does integrated memory remove H2D/D2H?

Short answer: on GB10, the bytes mostly no longer need to move. The hand-over between CPU and GPU still has to happen, and it now costs synchronization and complexity instead of PCIe bandwidth. At scale, the dominant cost is per-user execution, not memory.

1. Where data crosses between CPU and GPU in the CUDA gNB

The CUDA gNB does not run everything on the GPU. With every acceleration enabled (all), the split is:

2. Why sharing the same DRAM is not enough

Being in the same physical DRAM does not mean both processors may touch the same bytes at any time. Page tables, caches and the CUDA memory type decide who may access what and when:

CUDA memory typeCPU accessGPU accessUsed here for
Pageable host (malloc)yesonly via host page tables (GB10: yes; Orin, RTX 5090: no)radio buffers, CPU PHY
Pinned / registered hostyesyes (mapped)IQ buffers, pinned grids
Device (cudaMalloc)noyesGPU scratch, owned snapshots
Managed (cudaMallocManaged)depends on the attributes belowdepends on the attributes belowthe shared resource grid

The managed-memory rules come from three device attributes:

AttributeRTX 5090GB10OrinMeaning when 0
ConcurrentManagedAccess110The CPU must not touch any global managed page while any kernel in the context runs (Orin → D7).
PageableMemoryAccessUsesHostPageTables010The GPU cannot read ordinary host memory directly.
DirectManagedMemAccessFromHost000The CPU cannot read a GPU-resident managed page in place; the page must migrate back first.

GB10 is 1 / 1 / 0. So on GB10 the GPU can reach host data directly, but a host read of the grid after a GPU write still needs the pages brought home. The vendor code says this in its own comments: GB10 cannot CPU-load GPU-resident managed pages, and a D2H copy of the live managed address raised Xid 31. The vendor classifies only GH200-class parts (1 / 1 / 1) as fully coherent.

So on GB10 H2D/D2H has largely become D2D snapshots, page migration and synchronization. That is cheaper than PCIe, but it is harder to get right. Four of the defects in this work (D1, D2, D7 and the vendor's own 35b27de4d6 fix) are hand-over bugs.

5. What this means for many users (massive MU)

  • Per-PDU execution dominates. With 16 UEs × 17 PRB (4L4P): CPU 610 µs, GPU direct path 995 µs (62 µs per PDU, the same with --sync-after-process=0). The GPU becomes slower than the CPU as users are added, even with no copies.
  • Batching exists but is not connected. The same 16 UEs with cross-PDU transport-block batching (--encoder-batch=1): 140 µs (8.8 µs per PDU). The batch encoder (ldpc_encoder_cuda_batch, transport_block.cu) is in the vendor library, at the pin and at head 900d8d0e, but no gNB code calls it. Only the benchmark does, through the low-level API, so the 140 µs may not include everything the gNB processor does.
  • Small transfers multiply. Crossing ③ happens per PDU. Unified memory does not reduce per-call and per-sync overhead.
  • Shared bandwidth. On integrated parts the CPU and GPU draw from the same memory bandwidth, so heavy MIMO traffic makes them compete. Not measured.

6. What would actually remove the problem

  1. Hardware: full coherence (DirectManagedMemAccessFromHost = 1, GH200-class) removes snapshots and prefetch. GB10 and Orin do not have it.
  2. Software ownership: stop handing the grid back and forth within a slot. Either move the remaining grid writers (PDCCH, SSB, CSI-RS, PUCCH, PDSCH DM-RS) to the GPU, or collapse the hand-over to one point per slot. MAC and the scheduler can stay on the CPU; they exchange only small per-slot messages.
  3. Batching: wire cross-PDU batching into the gNB PDSCH path (and check PUSCH), so per-user overhead stops scaling with the number of UEs.
