One block represents 1 ms. Each receiver completed about 1,278–1,282 calls in the requested 10 s sequential benchmark, approximately 128 blocks/s. This describes that benchmark, not the concurrent broker capacity.
The aggregate median is dominated by 64 light UE-destination calls. The gNB destination combines 64 incoming streams. gpu_process_us excludes CPU preparation. A claim that these records prove 64 live UEs at real time is unsupported; the records themselves are internally consistent.
At 64 inputs, one block contains 64 * 23,040 * 8 = 11,796,480 input bytes. Host preparation largely packs these IQ buffers; it is channel-emulator work, not the gNB MAC scheduler.

Timing definitions and normalization
Channel wall intervals are entry/packing, model/control, receiver preparation, CUDA submission, stream-completion wait, and output/recording. Their sum is the channel call. The broker process interval additionally includes the profiling callback and CSV recording overhead.
CUDA H2D/kernel/D2H event intervals overlap host submission and completion waiting. Do not add them to host wall intervals. The kernel event interval spans multiple kernels and their gaps/competition; it is not a single pure arithmetic kernel.
Every reported mean normalized to one radio millisecond is sum(elapsed_us) / (sum(samples) / sample_rate_hz * 1000). Receiver calls can process fragments; a function call is not necessarily a radio slot.
CPU thread time can include active CUDA completion waiting and polling. It is not equal to useful preparation time. room_us is output headroom waiting; data_us waits for common input IQ. Those waits can arise from radio compute, transport, or broker-thread scheduling.

Nsight activity fractions are time with at least one captured kernel running, not SM occupancy. Post-API start delay includes ordered dependencies on earlier kernels in the same stream; it is not exclusively inter-process GPU contention. The successful captures are synthetic broker controls, not the complete MPS live stack.
Full live-stack launch under Nsight failed at unshare with Invalid argument before measurement. Live channel timings instead use receiver-local CUDA events and host timers. No complete live-stack GPU scheduling timeline is claimed.
The steady-window software cpu-clock event was unsupported on this kernel. A single hardware-cycle collector captured the second policy after applied update k >= 120 (past the 10-radio-second warmup), pinned to auxiliary cores 0–4. Its PMUs are separate for CPU classes; 59 lost samples and unresolved kernel symbols limit exact CPU percentage attribution.

Validation and practical limits
Release CUDA processing, runtime-update parity, matrix history and broker tests: 4/4 pass. The full initial suite also exposes a CPU parallel-reference parity failure reproduced in the pre-existing Spark binary. Production source and system tuning were not changed.
The Sionna channel trace is computed before measurement and replayed at 10 Hz; the ray-tracing solver is not an active GPU tenant during the timed RAN window. Thus these tests do not measure concurrent online ray-tracing load.
Real-time speed, deadline misses, connectivity and traffic validity are distinct. Preserve all failures; a near-1 sample ratio does not establish strict every-slot real-time qualification.
Historical PR10 two-cell CUDA 0.53 is not reproduced: the instrumented run advances at about 0.868/0.890 by IQ sample progress, and the tracing-off repeat reports about 0.867/0.877 by the gate scheduler-slot metric. Do not treat the old two-cell slowdown as a universal GPU-sharing result.
The direct measured result at 16 UEs is that most elapsed time is waiting around IQ exchange. The two-core broker allocation is itself a limit in its synthetic control; scheduler decision time alone is far smaller than the full cycle. A statement that MAC is the confirmed primary bottleneck would overstate these measurements.
