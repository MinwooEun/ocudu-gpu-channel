A · 프로그램 사이에 무엇이 오가나요?

인터넷 데이터가 아니라, 그 데이터를 실은 파형의 숫자가 오갑니다

기지국이 만든 파형을 숫자로 나열한 것이 IQ sample입니다. 채널 에뮬레이터는 이 숫자들을 바꿉니다. 멀어지면 작게 만들고, 반사가 있으면 지연된 복사본을 더하고, 잡음을 섞습니다. 단말은 바뀐 숫자를 받아 원래 데이터를 해석합니다.

위 파형은 원리를 보여 주는 설명용 값입니다. 실제 측정된 IQ나 성능 그래프가 아닙니다.

B · 이 안에서 CPU와 GPU는 어디에 있나요?

에뮬레이터의 CPU 코드가 일을 준비하고, GPU에 계산을 요청합니다

CPU와 GPU는 이 프로그램이 쓰는 계산 자원입니다. CPU 코드는 파형 숫자를 받고 → 어디에 있는지 확인하고 → 계산을 요청하고 → 완성된 결과를 보냅니다. GPU는 요청받은 파형 계산을 실행합니다. 그 GPU 실행 함수를 코드에서 kernel이라고 부릅니다.

여기서 “GPU를 쓴다”는 것은 채널 에뮬레이터의 계산 일부를 GPU에 맡긴다는 뜻입니다. 파형이 도착하는 일과 결과를 전달하는 일까지 자동으로 빨라지는 것은 아닙니다.
C · CPU preparation 76.7 µs는 이 그림의 어디인가요?

채널 함수에 들어온 뒤, GPU 작업을 제출하기 전까지 잰 이름입니다

기존 복사 모드에서는 CPU가 여러 입력 파형을 별도 배열에 다시 모으고, 채널 설정을 준비했습니다. 이 구간에 붙인 측정 이름이 host_prep_us, 즉 CPU preparation입니다. 기지국의 모든 CPU 처리나, 입력 파형이 도착하기를 기다리는 전체 시간은 포함하지 않습니다.

아래 그림은 가운데 채널 에뮬레이터 내부만 확대합니다. 프로그램 사이에서 파형을 주고받는 경로는 바깥에 그대로 있습니다.

측정 경계: 채널 함수 진입 → 입력 모으기·설정 준비 → GPU 작업 제출 직전.
CPU preparation은 이 앞부분의 이름입니다. GPU가 실제로 파형을 계산하는 시간은 뒤에 있습니다.

D · “Spark로 오면서 해결됐다”와 지금의 느린 실행은 어떻게 연결되나요?

큰 IQ 복사를 줄인 수정은 이미 적용된 기준 상태입니다

Spark의 CPU와 GPU는 메모리를 공유합니다. 에뮬레이터는 CPU가 입력 파형을 별도 배열로 다시 모으는 대신, GPU가 원래 입력 배열을 직접 읽는 경로를 갖고 있습니다. 이 수정은 0a6f281(Z8)로 통합됐습니다. 클로드가 말한 이 복사 문제의 해결은 기록과 코드에 맞습니다.

이번에 내가 측정한 Spark도 이미 그 수정이 적용된 경로입니다. 저장된 live trace에서 direct_in=1, zero_in=1, zero_out=1을 확인했습니다. 큰 IQ 입력 복사를 다시 병목으로 가정하고 측정한 것이 아닙니다.

같은 프로젝트 안에 서로 다른 실행 경로가 있습니다10월 13일 RTX benchmark는 복사 모드를 선택했습니다. 9월에 Spark용 최적화를 했어도 이 RTX 실험에는 복사 준비 시간이 나타납니다. 날짜가 나중이라는 이유만으로 Spark 직접 읽기 경로의 측정이 되는 것은 아닙니다.

01어떤 일을 재고 있었나

신호가 이동하는 길부터 보기

IQ는 무선 파형을 숫자로 표현한 sample입니다. PHY는 그 파형을 만들고 해석하는 물리계층 처리입니다. broker는 gNB·UE 사이에서 IQ를 받아 채널 계산을 맡기고 결과를 전달하는 중계 프로그램입니다.

그림에 나오는 프로그램·작업·버퍼는 무슨 뜻인가요?
ZMQ
서로 다른 프로그램이 IQ를 요청하고 응답으로 주고받는 메시지 통신 방식입니다.
worker
한 프로그램 안에서 독립적으로 실행되는 CPU 작업(thread)입니다.
producer
입력과 출력 공간을 확인하고 채널 함수를 호출하는 worker입니다.
ring
IQ를 잠시 담아 두는 순환 버퍼입니다. 결과를 쓸 공간이 남았는지도 확인해야 합니다.
각 상자를 눌러 역할을 확인하세요.

UL은 여러 UE 신호가 하나로 합쳐집니다

gNB가 듣는 신호에는 여러 UE의 신호가 함께 들어갑니다. 채널을 적용한 각 입력을 같은 sample 시각에 맞춰 합성합니다. 그래서 gNB 수신 producer는 모든 입력에 공통으로 존재하는 구간을 확인합니다.

DL은 UE마다 별도 결과가 필요합니다

하나의 gNB 송신 신호도 UE별 채널이 다릅니다. 16개 UE 목적지의 채널 처리와 결과 전달이 각각 존재합니다. gNB 수신 경로 한 개의 시간만으로 전체 작업량을 설명할 수 없습니다.

CUDA gNB라면 MAC·스케줄러도 GPU에서 하나요?

이번 gNB의 MAC과 무선 자원 스케줄러는 CPU에서 실행됩니다. CUDA 설정의 all은 지원하는 PHY 가속 단계 전체를 뜻합니다. UE PHY는 이 실험에서 CPU 경로입니다. 스케줄러 결정은 16 UE에서 평균 약 40 µs였으며, 현재 수 ms의 진행 간격을 이 결정 시간 하나로 설명하기 어렵습니다.

이 문서에서 “worker가 CPU 실행 차례를 기다린다”는 말은 OS의 thread scheduling입니다. UE에 무선 자원을 배정하는 MAC scheduler와 구분합니다.

여기의 2.2 ms는 무선 sample의 평균 진행 간격입니다. IP 패킷의 종단 간(E2E) 지연은 트래픽 큐, 재전송, 네트워크 처리까지 포함해 별도로 재야 합니다. 이 둘은 같은 지표가 아닙니다.

평균 진행률 1.0과 모든 deadline 충족도 별개입니다. 평균 속도가 맞아도 순간 지연·입력 starvation이 있으면 엄격한 실시간 검증에는 실패할 수 있습니다.

왜 “호출 1회 = 무선 1 ms”로 계산하면 안 될까요?

실제 radio가 IQ를 부분 chunk로 요청·공급하므로 채널 함수는 한 무선 ms를 여러 번에 나눠 처리합니다. 16 UE에서는 gNB 경로가 무선 ms당 약 2.1번 호출됐습니다. 따라서 한 호출의 약 78 µs만 보고 “전체 비용이 78 µs”라고 읽을 수 없습니다.

무선 ms당 구간 비용 = Σ(구간의 실제 소요 시간) ÷ [Σ(IQ sample 수) ÷ sample rate × 1,000]

또 “구간들이 차지하는 실제 시간”과 “CPU가 실행된 시간”은 다릅니다. 기다리는 동안 CPU가 잠들 수도 있고, 반복 확인하며 실행 시간을 쓸 수도 있습니다.

이번 호출에서 처리 가능한 무선 시간

설명용 batch 상한은 1 ms입니다. 실제 broker는 공통으로 준비된 부분 구간부터 처리할 수 있습니다. 0.25 ms가 있으면 그만큼 먼저 진행하고, 이후의 아직 없는 sample 구간에서 다시 기다립니다.

입력 대기 데이터가 아직 없을 때

UE의 CPU PHY가 IQ를 만드는 시간, ZMQ 요청·응답, puller가 실행되어 버퍼에 넣기까지의 시간이 앞에 있습니다. producer에서 잰 입력 대기는 이 결과를 기다리는 시간입니다. 1.58 ms를 전부 ZMQ 전송이나 CPU 준비 연산으로 분해한 값은 아닙니다.

출력 공간 대기 앞선 결과가 남았을 때

결과를 받는 radio가 아직 이전 IQ를 소비하지 않았거나, REP 전달이 늦으면 RX ring에 공간이 부족합니다. producer는 새 계산 전에 출력 공간부터 확인합니다. 상대의 소비가 늦으면 앞단의 진행도 함께 제한됩니다.

대기는 “병목이 드러난 위치”입니다긴 입력 대기는 공급 경로가 늦었다는 직접 증거입니다. 그 안에서 UE 연산, 전송, OS 실행 순서가 각각 얼마를 차지했는지는 별도 구간 계측이 필요합니다. 코어 수만 늘린 실험이 효과가 없었던 이유도 이 전체 연결을 함께 봐야 이해할 수 있습니다.

GPU event는 별도 시계로 잰 구간입니다

host 시간과 GPU event 시간을 더하면 중복 계산입니다CPU가 작업을 제출하거나 완료를 기다리는 동안 GPU가 실행됩니다. 예를 들어 함수 전체 약 163 µs와 GPU kernel event 약 109 µs는 겹칩니다. 둘을 더한 약 272 µs는 전체 처리 시간이 아닙니다.

여기서는 각 GPU event 구간의 길이를 표시하며 host와의 정확한 시작점 정렬을 그리지 않았습니다. kernel event에는 여러 kernel과 그 사이의 간격이 들어갑니다. H2D/D2H event라는 이름도 그 구간에 실제 IQ 복사가 있었다는 증거는 아닙니다.

RTX 5090의 “64 UE”는 어떤 실험이었을까요?

원본 52개 파일의 hash는 모두 일치했습니다. 기록은 실제로 있습니다. 다만 실제 gNB·UE·ZMQ가 연결된 live 실험이 아니라, 채널 함수를 순서대로 호출한 합성 benchmark였습니다.

모든 목적지를 섞은 호출 중앙값

가벼운 UE 목적지 호출 64개가 많이 들어 있습니다. 무거운 gNB 목적지 1개의 비용이 가려집니다.

gNB 목적지 호출 중앙값

UE 64개의 신호를 합칩니다. 한 block은 무선 1 ms인데 전체 호출 중앙값이 약 1.20 ms, p99는 약 1.34 ms입니다.

gNB 호출 안쪽에서 보였던 시간

3회 실행에서 각각 계산한 중앙값들의 중앙값입니다. 서로 다른 항목의 percentile을 더해 전체 percentile로 만들지 않습니다. CPU 준비는 IQ packing을 포함합니다.

64 × 23,040 sample × 8 byte ≈ 11.8 MB / block

이 경로의 큰 CPU 준비 시간은 channel emulator의 입력 packing입니다. gNB MAC 스케줄링 시간이 아닙니다. Spark의 direct/shared IQ 경로와 같은 비용 구조로 읽을 수 없습니다.

이 기록으로 64 live UE의 실시간을 증명할 수 없습니다약 10초 동안 목적지당 약 1,280번 호출된 순차 benchmark입니다. GPU kernel 구간만 짧다는 사실, 전체 목적지 중앙값, 실제 radio의 실시간 진행은 서로 다른 지표입니다.

최종 CPU stack은 warmup 이후 hardware-cycle 수집기 하나를 보조 코어에 고정했습니다. ARM kernel에서 software cpu-clock sampling이 지원되지 않았으며, hardware sample 59개 손실과 일부 미해석 kernel symbol이 있어 정확한 CPU 비중을 소수점 단위로 주장하지 않습니다.

Nsight의 약 31%는 무엇을 뜻하나요?

16-UE 합성 capture에서 kernel 실행 시간 구간들을 겹침 없이 합친 길이는 전체 kernel activity span의 약 31%입니다. 이 값은 SM occupancy가 아닙니다. 일부 startup도 포함하며 live 전체 capture도 아닙니다. kernel 제출 이후 시작까지의 시간에는 같은 stream의 이전 작업 의존성이 포함될 수 있습니다.

Sionna ray tracing이 측정 중 GPU를 같이 썼나요?

이 campaign에서는 채널 trace를 측정 전에 생성하고, 측정 중에는 sample-indexed 방식으로 10 Hz replay했습니다. timed window에서 ray-tracing solver가 별도 GPU tenant로 실행되는 조건이 아닙니다.

관련 소스의 실제 대기와 완료 확인 부분

별도 계측 snapshot 기준입니다. 입력은 모든 lane의 공통 구간을, 출력은 모든 row의 공간을 확인합니다.

용어를 한 번 더 정리하기
UE / gNB
단말 / 기지국. 이 실험에서는 실제 소프트웨어 radio process입니다.
IQ
무선 파형을 표현하는 복소수 sample. 이 경로의 complex-f32는 sample당 8 byte입니다.
broker
IQ를 받아 채널 계산을 수행하고 목적지에 결과를 전달하는 중계 프로그램.
ring / headroom
순환 버퍼 / 새 결과를 쓸 수 있는 빈 공간.
producer
입력 공통 구간과 출력 공간을 확인하고 채널 함수를 호출하는 worker.
H2D / D2H
host(CPU 측)→device(GPU 측) / 반대 방향의 명시적 복사.
kernel
GPU에서 실행되는 계산 함수.
starvation
이미 진행하던 수신 경로가 필요한 입력을 정해진 관측 기준 안에 얻지 못한 기록.
pacing
너무 빠르게 가지 않도록 무선 sample 속도에 맞추는 의도된 대기.
KPI 유효 구간
보고서의 지표 계산에 필요한 UE·slot 기록이 확보된 무선 1초 구간. 전체 연결 상태와 같은 뜻은 아닙니다.
