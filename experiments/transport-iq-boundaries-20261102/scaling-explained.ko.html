이 표는 보장된 최대값을 뜻하지 않는다. 경계에서 실행마다 결과가 갈린 점까지 범위로 남겼다. 평균 진행률이 1에 가까워도 개별 배치의 처리 시한(deadline)을 놓칠 수 있다. 아래에서 실제 반복값과 시한 검사를 함께 확인할 수 있다.

같은 “채널 테스트”라도 실행하는 일이 다르다

종류를 선택해 실제로 포함된 구간을 확인한다. IQ-only에도 CPU 준비와 CPU↔GPU 전달이 포함된다. GPU 커널 하나의 계산 시간만 따로 재는 구성이 아니다.

그림의 이름: radio node는 gNB나 UE 한 대의 송수신 포트 묶음이다. thread(스레드)는 CPU에서 실행되는 작업의 흐름이며, worker는 특정 일을 반복 처리하는 thread다. broker는 IQ 입출력과 채널 처리를 조정하는 채널 에뮬레이터 프로세스다.

① 함수의 처리 부하

메모리의 IQ를 각 수신 radio node의 채널 함수에 넣는다. UE 수는 가상 radio node 수를 정하는 값이다. 실제 UE 프로세스는 실행하지 않는다.

② 입출력을 포함한 부하

가상 IQ 송수신기와 broker 사이에 ZMQ를 연결한다. 실제 OCUDU radio_zmq 클래스나 srsUE RF 구현을 분리 실행한 실험은 아니다.

③ 실제 스택의 부하

CUDA gNB, CPU srsUE, 코어와 트래픽까지 실행한다. PHY·MAC 작업도 CPU/GPU 자원을 함께 사용한다. 이전 라이브 검증 결과는 아래 별도 표로 제시한다.

두 가지 “준비 시간”을 구분한다. 워밍업은 측정 전에 반복 실행하는 2초다. CPU 입력 준비는 매 배치마다 전송할 샘플을 버퍼에 모으고 채널 설정을 준비하는 작업이며, 채널 함수 호출 시간에 포함된다.
①·②는 같은 정적 8-tap TDL + 수신 잡음 모델을 사용한다. ③은 이동 Sionna 채널 갱신과 다른 CPU 배치를 사용한 별도 실험이므로 세 결과를 동일 조건의 차감 실험처럼 읽지 않는다.

축을 하나씩 바꾸면, 어떤 작업이 늘어날까

선택한 축만 바꾼다. 그림은 작업 구조를 설명하고, 그래프와 표는 실제 측정값을 보여준다. 데이터 worker 수는 소스 구조로 계산한 값이다. IQ는 수신 node당 1개, ZMQ broker는 포트마다 입력을 수집하는 puller와 응답을 보내는 REP worker를 두고, node마다 출력을 만드는 producer를 더한다. 별도 I/O·제어 thread는 이 수에 포함하지 않았다. CPU 실행 시간은 허용된 5코어 안에서 나눈다.

진행률 1.000은 무슨 뜻인가

IQ 샘플은 일정한 길이의 무선 시간을 나타낸다. 예를 들어 23.04 MS/s에서 샘플 23,040개는 무선 시간 1 ms에 해당한다. 이것을 묶어 처리하는 단위를 배치라고 부른다.

진행률 = 처리한 샘플이 나타내는 무선 시간 ÷ 실제 경과 시간

8초 측정에서 얼마를 처리했나

0.999875

8초에 8,000배치가 기준이다. 7,999배치는 7.999초의 무선 시간을 처리한 것이며, 소수점 오차로 나온 값이 아니다.

평균 처리량과 개별 시한은 따로 본다

한 번 늦게 처리한 뒤 다음 배치를 빠르게 처리하면 평균은 1.000에 가까워질 수 있다. 그래도 늦었던 배치의 deadline 위반 기록은 남는다.

이 실험의 처리량 판정은 측정창 경계에 걸치는 최대 한 배치를 명시적으로 허용한다. 1 ms 배치에서는 7,999/8,000 = 0.999875다. deadline 위반 0회를 뜻하는 판정은 아니다.

IQ-only는 절대 시각에 맞춰 호출하며 밀린 작업을 따라잡는다. ZMQ broker는 출력 버퍼가 감당할 수 있도록 따라잡을 지연을 한 배치로 제한한다. 이 pacing 동작 차이도 두 실행 범위의 일부다.

32 UE에서, 시간이 길어진 위치를 보면

아래는 ZMQ-only · 20 MHz · 1×1 · 32 UE의 대표 1회 측정이다. gNB 수신용 채널을 만드는 producer의 구간별 평균 wall time을 표시했다. 한 배치가 나타내는 시간은 1 ms다. 측정 위치는 broker 내부의 가상 gNB 수신용 출력 경로다.

출력 공간 확보 구간입력 준비 구간입력 링 읽기채널 함수 호출
측정된 위치: RTX에서는 채널 함수 호출이 평균 2.696 ms로 1 ms 배치 시간을 넘었다. Spark에서는 출력 공간 확보 구간 1.029 ms와 입력 준비 구간 0.543 ms가 큰 부분을 차지했다.

구간의 wall time에는 스레드가 다시 실행될 때까지의 시간도 포함된다. 따라서 “출력 버퍼가 이 시간 내내 차 있었다”로 바꿔 읽을 수 없다. 채널 함수 시간은 CPU 준비·복사·GPU 작업·동기화를 포함한다. 위 막대는 pacing·출력 push·그 외 bookkeeping 시간을 제외한 구간 합이다.

채널 처리 CPU 5개를 실제로 얼마나 사용했나

32 UE에서 broker CPU 사용량은 허용된 5개 코어에 거의 도달했다. 개별 연산의 원인은 이 평균 CPU 사용량만으로 정하지 않는다. CUDA runtime 작업과 CPU에서 수행하는 대기도 CPU 시간을 사용할 수 있다.

채널 CPU가상 송수신기 CPU관측·기록 CPU배정하지 않은 코어

코어 색은 실행을 허용한 범위이며 점유 예약을 뜻하지 않는다. OS·데스크톱 작업과 공유될 수 있다. 장비의 CPU 구조, 가상 송수신기 CPU 배정, 드라이버와 메모리 경로가 다르므로 GPU 연산 코어 성능만의 비교로 읽지 않는다.

라이브 스택 결과는 어디에 놓아야 할까

이 표는 앞서 실제 CUDA gNB + CPU srsUE로 검증한 UE 축이다. 이동 Sionna 채널, 20 MHz·23.04 MS/s·1×1, 준비 구간 이후 약 29.9초의 무선 시간으로 진행률을 계산했다.

RTX의 배치 교환은 gNB와 broker 사이에서 P/E 코어 2개씩을 교환한 실험이다. 역할별 코어 수는 유지했다. 위 격리 실험의 “채널 처리 코어 5개”와는 다른 배정이다.

16 UE의 KPI와 완료 여부
RTX 기본 실행의 유효 KPI 3/30은 UE1 metrics 행이 27구간에서 빠져 제외된 결과다. 이를 27번의 통신 실패로 읽지 않는다. 배치 교환 실행은 IQ 진행이 10초간 멈춰 중단됐다. Spark 완료 실행에서는 SR 재시도가 관측됐다.
격리 결과와 함께 읽는 방법
IQ-only는 계산 호출의 처리 부하를, ZMQ-only는 입출력·버퍼·스레드 서비스가 추가된 부하를, 라이브는 실제 PHY/MAC까지 포함한 동작을 보여준다. 라이브의 문제를 ZMQ 단독 한계로 바로 옮겨 설명하지 않는다.

64 UE 기억을 다시 확인한 조건

빠른 코어를 모두 사용하는 추가 IQ-only 검사도 3회씩 실행했다. RTX는 P코어 8개, Spark는 X925 10개를 썼다. gNB 하나와 64 UE의 총 65개 RX node를 함께 처리한 결과다.

예전 fan-in 자료에서 gNB 한 번의 호출 지연을 보여준 그래프는 전체 수신 노드가 매 주기 처리됐다는 증거가 아니다. 이번 표와 그래프는 모든 RX 중 가장 느린 수신자의 진행률을 사용한다.

채널 CUDA backend를 포함한 archive member 12개는 유지하고, broker의 broker.cpp.o만 측정 카운터를 추가해 교체했다. 카운터는 메모리에 모은 뒤 측정 종료 후 저장했다. 가상 송신기의 반복 sin/cos 계산을 캐시로 바꾼 결과는 두 장비에서 기존 송신기와 각각 16,220,160 byte를 실제 ZMQ로 비교해 일치했다.

정식·대조 실행은 모두 프로그램/peer health 확인을 통과했다. 측정된 ZMQ IQ의 평균 power는 유한한 양수였고, broker의 ZMQ 오류·queue overflow·sequence gap은 0이었다. 이 항목들은 속도나 deadline 검사와 따로 확인했다.

판정 기준과 재현 방법

각 실측점의 표에서 “처리량 기준 충족”은 해당 측정창에 예상되는 배치 수에서 창 경계 한 배치를 뺀 값 이상을 처리했는지다. “deadline 검사 충족”은 IQ에서는 예정 시각 뒤에 완료한 배치가 없었는지, ZMQ에서는 producer pacing rebase와 배치 시간보다 긴 채널 호출이 없었는지다. 반복 횟수가 1회인 점도 있으므로 표의 측정 횟수를 함께 읽는다.

IQ-only worker는 첫 채널 계산 완료를 모두 확인한 뒤 공통 준비·측정 시각을 시작했다. 초기 타이머만으로 측정창을 열었던 시도는 별도 자료로 남겼다. ZMQ 측정 카운터를 끈 대조에서도 16 UE의 처리량 손실이 유지됐다.
