IQ를 기다리는 동안 CPU를 비워 주는 패치

대상은 DGX Spark에서 실행하는 CUDA gNB + 기존 CPU srsUE + GPU 채널 에뮬레이터다. UE GPU 구현은 이 비교에 사용하지 않는다. PR10의 16 UE, 1 cell, 20 MHz, 23.04 MS/s, 1×1 입력을 고정한다.

무엇을 고치는가

이전 함수 단위 측정에서, gNB 방향 producer가 입력 준비를 확인하기까지 걸린 541.443 µs 중 515.593 µs는 실제 sched_yield() 호출 안에서 흘렀다. 입력을 계산하는 시간이 아니라 실행 가능한 스레드들이 같은 CPU를 두고 차례를 기다리는 시간이 대부분이었다. 수치는 표현된 무선 시간 1 ms당이며, 전체 라이브 실행 시간의 비율과는 다르다.

16 UE와 gNB 하나에는 17개 노드가 있다. 기존 구조는 입력 수신 17개 + 채널 처리 17개 + 응답 17개, 총 51개의 애플리케이션 작업 스레드를 두었다. 이들이 배정받은 broker CPU는 15–16의 두 코어다. ZMQ 내부 I/O, CUDA 내부 스레드와 메인 스레드는 이 51개에 포함하지 않는다.

통신 루프는 기다려야 하는 ZMQ 호출을 하지 않는다. 한 UE가 데이터를 보내지 않거나 응답을 받지 않아도 다른 포트를 처리할 수 있다. GPU 호출과 pacing 대기도 통신 루프 밖에서 처리한다. eventfd는 에뮬레이터 내부에서만 쓰는 알림이며, UE/gNB가 보는 ZMQ 주소·요청·cf32 IQ 메시지는 바뀌지 않는다.

반드시 유지하는 동작

  • 노드마다 샘플 순서·입력 cursor·채널 상태·pacer를 하나만 유지한다.
  • MIMO의 모든 출력 포트는 같은 시작 샘플과 같은 길이를 공유한다.
  • 입력이 일부만 준비된 경우도 처리한다. 매번 한 배치 전체를 요구하면 lock-step 무선 스택이 멈출 수 있다.
  • 실제 IQ를 버리거나 빈 IQ로 채우지 않는다. ZMQ 메시지를 전송할 때까지 필요한 버퍼를 유지한다.
  • 기존 실시간 pacing과 한 배치의 지연 부채 한도를 유지한다. 알림이 와도 pacing 마감 시각을 앞당기지 않는다.
  • 알림 직전에 입력이 도착한 경합을 세대 번호로 처리한다. 큐에 늦게 복귀해도 이미 지난 starvation을 누락하지 않는다.

측정 결과

검증 진행 중. 최종 수치와 유효 구간·오류 카운터를 이 위치에 기록한다.

트래픽 측정 구간 완료는 엄격한 실시간 통과와 다르다. 속도 1.0 미만이나 starvation이 남으면 실시간 병목이 해결됐다고 판정하지 않는다. queue_us는 준비 큐 등록부터 작업자 실행까지의 누적 시간이며, 이전 515.593 µs와 측정 경계가 같지 않다.

재현 및 근거

비교 스위치는 OCG_BROKER_READY_WORKERS=0 (기존), =2 (producer 큐), 여기에 OCG_BROKER_MULTIPLEX=1을 추가한 통신 루프다. 기본 실행 방식은 기존 방식이며 새 경로는 명시적으로 선택한다.

원본 PR10 frozen channel/traffic bundle, CUDA gNB 및 CPU srsUE, MPS, CPU 배치를 그대로 사용한다. 원래 실험에 필요했던 샘플 기준 제어 패치는 c66de51로 별도 복원했다. 최초 link_clock 오류 실행과 별도 빌드가 겹친 첫 기준 실행은 성능 비교에서 제외한다.
